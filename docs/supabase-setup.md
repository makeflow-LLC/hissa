# الجزء الأول: ما تفعله بنفسك

## الخطوة ١: إنشاء حساب Supabase

1. افتح [supabase.com](https://supabase.com)
2. اضغط **Start your project** (أعلى اليمين)
3. سجّل الدخول بحساب GitHub — الأسهل لأن مشروعك على GitHub أصلاً

الحساب المجاني كافٍ تماماً للتطوير والتجربة.

## الخطوة ٢: إنشاء المشروع

1. اضغط **New project**
2. املأ الحقول:

| الحقل | ماذا تضع | لماذا |
|---|---|---|
| **Name** | `hissa` | اسم المشروع |
| **Database Password** | اضغط **Generate a password** | ⚠️ **انسخها واحفظها فوراً** في مكان آمن — لن تظهر مرة أخرى |
| **Region** | `Central EU (Frankfurt)` | أقرب منطقة للشرق الأوسط = أسرع استجابة للطلاب |
| **Pricing Plan** | Free | يكفي الآن |

3. اضغط **Create new project** وانتظر ٢–٣ دقائق حتى يجهز

> **تنبيه:** كلمة مرور قاعدة البيانات مختلفة عن كلمة مرور حسابك. احفظها في مدير
> كلمات مرور أو ملف آمن خارج المشروع. لو ضاعت يمكن إعادة تعيينها لكنها وجع رأس.

## الخطوة ٣: نسخ المفاتيح

بعد جهوز المشروع:

1. من القائمة الجانبية اضغط **⚙️ Project Settings**
2. اختر **API** (أو **API Keys** في الواجهة الجديدة)
3. ستجد ثلاث قيم — انسخها:

| القيمة | الشكل | الاستخدام |
|---|---|---|
| **Project URL** | `https://xxxxx.supabase.co` | عنوان مشروعك |
| **anon / publishable key** | `eyJhbGci...` أو `sb_publishable_...` | 🟢 **آمن** — يُستخدم في المتصفح |
| **service_role / secret key** | `eyJhbGci...` أو `sb_secret_...` | 🔴 **سري جداً** — الخادم فقط |

### ⚠️ أخطر خطأ يقع فيه المبتدئون

المفتاح السري (`service_role`) **يتجاوز كل قواعد الحماية**. من يحصل عليه يستطيع
قراءة وحذف كل بيانات منصتك.

**القاعدة:** أي متغير يبدأ اسمه بـ `NEXT_PUBLIC_` يُرسل إلى متصفح كل زائر.

```
✅ NEXT_PUBLIC_SUPABASE_ANON_KEY     ← صحيح، هذا المفتاح مصمم ليكون عاماً
❌ NEXT_PUBLIC_SUPABASE_SERVICE_KEY  ← كارثة! لا تفعل هذا أبداً
✅ SUPABASE_SERVICE_ROLE_KEY         ← صحيح، بلا NEXT_PUBLIC_
```

## الخطوة ٤: وضع المفاتيح في المشروع

أنشئ ملفاً جديداً باسم `.env.local` في جذر المشروع (بجانب `package.json`)
وضع فيه:

```bash
NEXT_PUBLIC_SUPABASE_URL=https://xxxxx.supabase.co
NEXT_PUBLIC_SUPABASE_ANON_KEY=المفتاح_العام_هنا
SUPABASE_SERVICE_ROLE_KEY=المفتاح_السري_هنا
```

**هل هذا الملف آمن؟** نعم. ملف `.gitignore` في المشروع يحتوي على `.env*` أي أن
Git يتجاهله ولن يُرفع إلى GitHub أبداً. تحقق بنفسك:

```bash
git status
```

إذا لم يظهر `.env.local` في القائمة فأنت بأمان. ✅

## المرحلة ٢: إنشاء الجداول

**ماذا يحدث:** إنشاء جداول قاعدة البيانات التي تقابل بياناتك الحالية.

| ملفك الحالي | الجدول الجديد |
|---|---|
| `lib/teachers.ts` | `teachers`, `units`, `lessons`, `live_sessions` |

**كيف تنفّذ SQL بنفسك (إن أردت):** من لوحة Supabase اضغط **SQL Editor** ثم
**New query**، الصق الكود، واضغط **Run**.

**كيف تتأكد أنها نجحت:** اضغط **Table Editor** في القائمة الجانبية — سترى
الجداول الجديدة فارغة.

## المرحلة ٣: تفعيل الحماية (RLS)

**ماذا يحدث:** تفعيل Row Level Security وكتابة سياسات الوصول.

**لماذا هذه أهم مرحلة:** بدونها أي شخص يملك مفتاحك العام يستطيع قراءة كل
بياناتك — حتى المحتوى المدفوع. مع RLS تصبح الحماية داخل قاعدة البيانات نفسها،
فلا يمكن تسريب المحتوى حتى لو أخطأت في كود الواجهة.

مثال على سياسة حقيقية ستُطبَّق:

```sql
-- المشتركون النشطون فقط يرون دروس المعلم
create policy "subscribers_read_lessons"
on lessons for select
using (
  exists (
    select 1 from subscriptions s
    where s.teacher_id = lessons.teacher_id
      and s.student_id = auth.uid()
      and s.status = 'active'
  )
);
```

**كيف تتأكد أنها نجحت:** في **Table Editor** بجانب كل جدول ستجد كلمة
**RLS enabled**. ولو حاولت قراءة جدول من متصفح بلا تسجيل دخول ستحصل على
نتيجة فارغة بدل البيانات.

> ⚠️ إذا نسيت تفعيل RLS على جدول واحد، Supabase سيحذرك في صفحة
> **Advisors** — راجعها دائماً.

## المرحلة ٥: القراءة من القاعدة

**ماذا يحدث:** الصفحة الرئيسية وصفحات البروفايل والدروس تقرأ من Supabase
بدل الملف الثابت.

**تغيير مهم ستلاحظه:** حالياً كل الصفحات ثابتة (`generateStaticParams`).
مع قاعدة بيانات ستنتقل إلى **ISR** — أي تُبنى الصفحة وتُحدَّث تلقائياً كل
فترة (مثلاً `export const revalidate = 60` = كل دقيقة).

**كيف تتأكد أنها نجحت:** غيّر اسم معلم من **Table Editor** مباشرة، حدّث
الصفحة الرئيسية — سترى الاسم الجديد. 🎉 هذه أول لحظة تشعر فيها أن المنصة
صارت حقيقية.

## المرحلة ٦: تسجيل دخول حقيقي

**ماذا يحدث:** استبدال الدخول التجريبي (كلمة المرور `123456`) بـ Supabase Auth
ببريد وكلمة مرور حقيقيين، مع حماية مسارات لوحة التحكم عبر Middleware.

**كيف تتأكد أنها نجحت:** سجّل حساباً جديداً، ثم افتح **Authentication →
Users** في لوحة Supabase — سترى المستخدم الجديد.

فتظهر لكل الطلاب على كل الأجهزة.

## المرحلة ٨: الفيديو

**⚠️ نصيحة مهمة: لا تخزّن الفيديوهات في Supabase Storage.**

السبب أنه يخدم الملف كما هو — بلا تحويل جودات وبلا بث تكيّفي. الطالب بإنترنت
ضعيف سينتظر تحميل ملف ٥٠٠ ميغا كاملاً، وستستهلك حصتك (١ غيغا مجاناً،
١٠٠ غيغا بـ ٢٥$ شهرياً) في أيام.

**الحل:** خدمة فيديو متخصصة تحوّل الفيديو تلقائياً لعدة جودات:

| الخدمة | التكلفة التقريبية | ملاحظة |
|---|---|---|
| **Bunny Stream** | ~٥$ شهرياً + سنتات لكل غيغا | 👍 الأنسب — الأرخص بفارق كبير |
| Cloudflare Stream | ~٥$ لكل ١٠٠٠ دقيقة تخزين | جيد |
| Mux | الأغلى | ميزات احترافية |

في قاعدة البيانات تحفظ `video_id` فقط، والفيديو نفسه عند Bunny.

**التقسيم النهائي:**

```
Supabase Postgres  →  كل البيانات
Supabase Storage   →  الصور والملفات
Bunny Stream       →  الفيديوهات فقط
```

| الخطأ | النتيجة | الوقاية |
|---|---|---|
| وضع `service_role` في `NEXT_PUBLIC_` | تسريب كامل للبيانات | راجع الخطوة ٣ |

| تنفيذ كل المراحل دفعة واحدة | لا تعرف مصدر الخطأ | مرحلة واحدة كل مرة |
| اختيار منطقة بعيدة | بطء دائم لا يمكن إصلاحه لاحقاً بسهولة | Frankfurt |

# ماذا لو تعطّل شيء؟

1. **صفحة Logs** في لوحة Supabase تعرض كل الطلبات وأخطاءها
2. **صفحة Advisors** تنبهك للمشاكل الأمنية وأداء الاستعلامات
3. **نتيجة فارغة بلا خطأ** = غالباً سياسة RLS تمنع القراءة، وليس عطلاً
4. كل مرحلة في فرع منفصل — يمكنك التراجع عن أي مرحلة بلا خسارة
